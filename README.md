# Agenta on Railway

A one-click Railway template that runs **[Agenta](https://github.com/agenta-ai/agenta) OSS** — the
open-source LLMOps / agent-engineering platform — as a complete, self-hosted stack: web studio,
API, workflow services, agent runner, Postgres, Redis, a durable S3-compatible object store and
the auth core. Everything except one HTTPS entrypoint stays on Railway's private network.

> Unofficial community template. It deploys the **official Agenta container images**
> (`ghcr.io/agenta-ai/*:v0.121.5`) unmodified; this repo only adds the small wrappers Railway
> needs (gateway, Postgres init, Redis volume perms, SeaweedFS IAM, API startup ordering).

|---|---------|--------|--------|--------|---------|
| 1 | **gateway** | this repo (`gateway/Dockerfile`) | ✅ HTTPS domain | `/healthz` | Single nginx entrypoint; routes `/`, `/m`, `/api/`, `/services/` |
| 2 | **web** | `ghcr.io/agenta-ai/agenta-web:v0.121.5` | — | — | Next.js desktop studio |
| 3 | **web-mobile** | `ghcr.io/agenta-ai/agenta-web-mobile:v0.121.5` | — | — | Mobile studio, served at `/m` |
| 4 | **api** | this repo (`api/Dockerfile`) | — | `/health` | FastAPI core + JWKS for the store |
| 5 | **services** | `ghcr.io/agenta-ai/agenta-services:v0.121.5` | — | `/health` | Workflow invocation runtime |
| 6 | **runner** | `ghcr.io/agenta-ai/agenta-runner:v0.121.5` | — | `/health` | Agent execution harness |
| 7 | **worker-streams** | `ghcr.io/agenta-ai/agenta-api:v0.121.5` | — | — | Tracing / events / records consumers |
| 8 | **worker-queues** | `ghcr.io/agenta-ai/agenta-api:v0.121.5` | — | — | Webhooks, triggers, interactions, evaluations |
| 9 | **cron** | `ghcr.io/agenta-ai/agenta-api:v0.121.5` | — | — | Scheduled jobs (supercronic) |
| 10 | **alembic** | `ghcr.io/agenta-ai/agenta-api:v0.121.5` | — | — | One-shot DB bootstrap + migrations |
| 11 | **supertokens** | `supertokens/supertokens-postgresql:11` | — | — | Auth core (sessions, API keys) |
| 12 | **Postgres** | this repo (`postgres/Dockerfile`) | — | — | `agenta_oss_core`, `agenta_oss_tracing`, `agenta_oss_supertokens` |
| 13 | **redis** | this repo (`redis/Dockerfile`) | — | — | Cache / queues / streams (AOF, volume-backed) |
| 14 | **seaweedfs** | this repo (`seaweedfs/Dockerfile`) | — | — | Durable object store with STS/OIDC IAM |

**Routing** (all through `gateway`):

```
/            -> web            (Next.js desktop studio)
/m, /m/*     -> web-mobile     (basePath /m, prefix NOT stripped)
/api/*       -> api            (prefix stripped; API is also prefix-tolerant)
/services/*  -> services       (prefix stripped)
/healthz     -> gateway itself (Railway healthcheck)
```

Only the gateway gets a public domain. Postgres, Redis and SeaweedFS are **never** exposed
publicly — they are reached over `<service>.railway.internal`.

## Deploy

> Template link: `https://railway.com/deploy/tgcFR5` (see
> [Template maintenance](#template-maintenance) to republish after a change).

1. Click **Deploy on Railway**.
2. (Optional) Set `AGENTA_LICENSE` — leave the default `oss`.
3. Railway provisions ~14 services and generates every secret.
4. **Attach the four volumes** — see [Volumes](#volumes). Do this before creating real data:
   without them Postgres, Redis and SeaweedFS start from scratch on every deploy.
5. First deploy takes **~8–15 min**: Railway builds five small wrapper images and the Agenta
   images are pulled cold. The `alembic` service creates the three databases and migrates them;
   `supertokens`, the API and the workers wait for that (or retry until it is done).
6. Open the gateway URL and **create the first account** (it becomes the instance admin).

### Secrets

Every credential is generated by Railway at deploy time and never stored in this repo:
`AGENTA_AUTH_KEY`, `AGENTA_CRYPT_KEY`, `AGENTA_SERVICES_INTERNAL_KEY`, `AGENTA_RUNNER_TOKEN`,
`POSTGRES_PASSWORD`, and SeaweedFS's `AGENTA_STORE_ACCESS_KEY` / `AGENTA_STORE_SECRET_KEY` /
`AGENTA_STORE_SIGNING_KEY`. `api` and `services` share one generated
`AGENTA_SERVICES_INTERNAL_KEY`; web, web-mobile, api and services share `AGENTA_AUTH_KEY`.

### Volumes

Railway's service filesystem is ephemeral, so anything that must survive a redeploy needs a volume.
This stack needs four — create them right after the first deploy, before storing real data:

| Service | Mount path | Why |
|---------|-----------|-----|
| `Postgres` | `/var/lib/postgresql/data` | All Agenta data (core, tracing, supertokens schemas) |
| `redis` | `/data` | Cache, queues and streams (AOF) |
| `seaweedfs` | `/data` | Durable object store (assets, prompt artifacts) |
| `api` | `/var/lib/agenta` | Durable RSA key for object-store mount URLs; without it the key is regenerated every redeploy and old signed URLs break |

Dashboard: open the service → **Volumes → Add Volume**, and use the mount path above.

CLI:

```bash
railway volume --service Postgres   add --mount-path /var/lib/postgresql/data
railway volume --service redis      add --mount-path /data
railway volume --service seaweedfs  add --mount-path /data
railway volume --service api        add --mount-path /var/lib/agenta
```

Attaching a volume redeploys that service, so the stack bounces once; Postgres runs `initdb` on the
fresh volume, `alembic` re-applies the migrations, and the `redis` wrapper chowns `/data` on boot.

> Volumes are not part of the published template — Railway's snapshot does not carry them, so the
> table above is the source of truth.

## Cost

This is a **14-service** stack with four always-on stateful services. On Railway's Hobby plan the
included `$5`/month credit does **not** cover it. Order of magnitude while fully idle:

| Component | Rough monthly |
|-----------|---------------|
| 8 always-on app services (api, services, runner, 2× web, 2× worker, cron) @ ~0.3–0.6 GB | ~$15–30 |
| Postgres + Redis + SeaweedFS + gateway + supertokens | ~$8–15 |
| Volumes (Postgres ~1 GB, Redis, SeaweedFS) | ~$1–2 |
| **Total** | **~$25–45 / month** |

Railway bills per-second for actual usage, so cost scales with traffic. To reduce it:

- Put `web`, `web-mobile`, `worker-*` and `runner` on **sleep mode** (Serverless); they wake on
  request.
- Delete `web-mobile` and `runner` if you don't use the mobile app or agent runs.
- Lower resource limits on the workers.

## Post-deploy

1. **Create the first user** at the gateway URL (it becomes admin).
2. **Add a model provider key**: *Settings → Models / Providers* (stored in Agenta's vault). An
   external or self-hosted OpenAI-compatible endpoint works too.
3. *(Optional)* `COMPOSIO_API_KEY` on `api` and `services` enables Composio tools and triggers;
   without it those planes stay hidden.
4. *(Optional)* `DAYTONA_API_KEY` (plus `AGENTA_RUNNER_DAYTONA_*`) on `runner` moves sandboxes to
   Daytona; the default provider is `local`.
5. *(Optional)* `SMTP_*` or `SENDGRID_API_KEY` on `web` enables signup emails; the web entrypoint
   derives the flags automatically.

## Troubleshooting

**Gateway returns 502/504 right after deploy.** An upstream is still starting; the workers and
`supertokens` also restart a few times until Postgres and Redis are ready. Wait for the `api` and
`services` healthchecks to go green in the Railway dashboard. The gateway re-resolves Railway
private DNS every 5 s, so a redeploy of an upstream recovers within seconds.

**`supertokens` keeps restarting on first boot.** It started before `alembic` created
`agenta_oss_supertokens`. It recovers once migrations finish; if it exhausted its retries, redeploy
it. The bundled Postgres image also creates the three databases at `initdb` time.

**`redis` crash-loops with `MISCONF ... unable to persist`.** The `/data` volume is root-owned.
The Redis wrapper chowns it before starting; make sure `RAILWAY_RUN_UID=0` and `RAILWAY_RUN_GID=0`
are set on the `redis` service (the template sets them).

**Agent file writes are silently lost / mount signing 503.** SeaweedFS is unhealthy or its IAM
config is wrong. Check that `AGENTA_STORE_JWT_ISSUER` on `seaweedfs` equals
`http://api.railway.internal:8000/api` and that `api` is healthy (it serves
`/api/.well-known/jwks.json`).

**Reset / start over.** Delete the `Postgres`, `redis`, `seaweedfs` and `api` volumes in the
dashboard, then redeploy — `alembic` recreates and migrates the databases.

## Template maintenance

To bump Agenta, replace the `vX.Y.Z` tag in every service that references
`ghcr.io/agenta-ai/agenta-*:vX.Y.Z` and in the `FROM` line of `api/Dockerfile`; `alembic` runs the
new migrations on the next deploy. `agenta-web-mobile` first shipped at `v0.111.0`, so never pin the
app services below it.

This repo is the source of the wrapper images and of the docs. The marketplace overview lives in
`TEMPLATE.md` — Railway requires the sections `# Deploy and Host`, `## About Hosting`,
`## Why Deploy`, `## Common Use Cases`, `## Dependencies for` and `### Deployment Dependencies`,
and caps it at 10 000 characters. Publish and update it with:

```bash
railway templates publish <template-id> --category "AI/ML" \
  --description "Agenta (open-source LLMOps) on Railway - 14-service OSS stack" \
  --readme-file TEMPLATE.md --demo-project <project-id>
railway templates update  <template-id> --readme-file TEMPLATE.md   # after edits
```

Or in the dashboard: **Project → Settings → Share / Publish as Template**. Mark the generated
secrets as generated variables, and write bare URLs as markdown links — the marketplace strips
autolinks and raw URLs.

Layout: `gateway/` (nginx edge), `api/` (wrapper over `agenta-api`), plus the `postgres/`, `redis/`
and `seaweedfs/` stateful wrappers; other services use the pinned Agenta images.
